# 创建问答与输出

先核对上下文，已回答的问题不重复提问。按阻塞程度分批问，避免一次收集所有运维参数。

## 第一批：最小必要问题

1. 新系统显示名称是什么？技术标识使用什么 slug（小写字母开头，只含小写字母、数字、短横线，最长 48 字符，不能仍叫 alife）？中英文显示名可以另外保存，技术标识不代替双语名称。
2. 选择 Azure + Cloudflare，还是纯 Cloudflare？不要根据是否已有 Azure 自动替用户选择。
3. 是否已有**供新系统独立使用**的 Azure Functions 与 Azure SQL？分别回答已有/没有/不确定。纯 Cloudflare 路线不需要 Azure；有 Azure 资源也不意味着必须使用。
4. 是否已有可用于新系统的 Cloudflare 账号与资源？只收集资源是否可用，不在聊天或项目配置里索要明文密钥。

## 实施前按需补充

- 目标项目目录、Alife 参考源码位置及版本、代码和资产复用权利。插件不依赖当前机器固定路径，也不默认有 GitHub 权限。
- 默认保持 Alife 的功能范围和英中双语形状；缩减/新增功能需明确记录。先区分“与指定版本现有能力一致”和“完成该版本所有目标功能”。
- 品牌/标志、初始教会或组织名称、时区、域名和 WebAuthn RP ID/origins；不知道域名时先做本地开发，生产身份配置仍待决定。
- 新数据库、R2、Worker、KV、AI session 和密钥隔离；已有资源不得默认指向 Alife 生产资源。
- LINE、YouTube、邮件和 AI 是否启用及选用何种已授权提供者。纯 Cloudflare 指自有应用运行与持久化设施；这些第三方能力的外部依赖仍需单独说明。不自动改换提供者、不自动增加付费服务。
- 初始化只用虚构测试数据或用户明确提供的合法配置，不复制成员/联系人/报名/凭据数据。真实数据导入是另一个有明确授权的任务。

## 首次输出

输出系统配置、源版本、所选架构、功能/契约到实现的 parity register、依赖顺序的工作台账，以及仍需决定的项目。每项能力单独记录 implementation 和 verification。计划阶段的输出明确标记为计划；后续交付逐步补充应用代码、测试和证据。

插件临时名为 alife-system-factory，后续可改插件品牌。这个插件名不是生成的产品名。
