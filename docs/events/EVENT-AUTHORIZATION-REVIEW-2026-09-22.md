## 去哪里设置，谁负责

| 层级 / 职责 | 设置入口与现有控制 | 边界 |
| --- | --- | --- |
| 平台角色 | 系统管理 → 角色与权限；活动权限可按 `admin.events.` 筛选 | 目录由服务端提供，不因角色名称推断权限 |
| 小组负责人 / 协同负责人 | 对应小组的成员与管理职责 | 不自动取得某场活动整体编辑权或全部专项数据权限 |
| 活动总负责人 | 创建时确立；活动工作台负责整体方案、职责配置、报告采纳、正式提交与发布 | 当前组成员资格、审批冻结和每次服务端校验仍有效；只有总负责人可提交正式审批 |
| 模块负责人 | 筹备 → 人员与职责；邀请后本人接受 | 仅当前活动及获授模块；离组、结束或撤销后不能沿用旧链接 |
| 普通任务执行 / 复核 | 任务与交接 → 明确执行人和复核人 | 完成普通任务不能代替 RAM、专项条件或整体审批 |
| 正式审批 | 正式审批页；按轻量、标准、增强治理等级解析审批人 | 标准/增强提交人与审批人分离；增强审批还检查相关专项作者 |
| 限时审批委派 | 正式审批 → 限时委派；所属组织领导或 `admin.events.managePackagePolicies` 管理 | 政策先启用；组织成员、范围、期限、撤销和职责分离继续校验；不是编辑授权 |
| 场地目录 / 活动预订 | 教会或小组场地管理 / 活动场地安排 | 管理共享场地与为某场活动预订是两种不同权限 |
| 双语翻译 | 活动资料及指定公开报名说明字段旁的既有 AI 补全按钮 | 只发送当前字段文字；翻译服务不授权保存、审批或发布 |

## 已确认并修正：正式审批仅总负责人提交

原先 `EVENT-WORKSPACES.md` 写总负责人独自提交，而机器契约和 `CanSubmitAsync` 允许已接受的 `event.lead`。用户选择“仅活动总负责人提交”。现命令与能力投影共同使用 `EventWorkAccess.OwnerAsync`，检查当前归属与有效小组成员资格；机器契约、专项说明和权限指南同步。生成/提交错误消息不再误称小组领导可代办。新增测试覆盖现场负责人、组负责人、协同负责人、普通成员被拒、总负责人成功，以及离组总负责人即便保留现场职责也被拒。历史提交与决定不回写，独立审批与执行授权不变。

## 已确认并对齐的现有权限边界

1. **撤回审批包。** 原机器契约额外列出了所属小组领导。用户确认保留 `WithdrawAsync` 和能力投影的现行边界：须有当前审批包查看权，且是生成者、提交者或当前总负责人；小组领导不自动获得撤回权。JSON 与专项文档已统一；新增断言检查组负责人、协同负责人、现场负责人和普通成员不能代撤回，总负责人可以撤回。撤回审批包不是撤销已批准决定。
2. **场地目录与活动预订。** 原机器规则将活动总负责人及资源协调人列为目录管理员。用户确认保留 collaboration v1 的分离：管理场地目录需该场地管理小组的负责人/协同负责人或现有平台管理授权；活动总负责人或已接受资源协调人只能凭活动职责预订获准场地。JSON、专项说明与权限指南已统一，不修改现行服务端规则。新增两个角色案例验证可预订根教会共享场地、不能修改目录，而目录管理员可修改。

以上是源码与规范比对发现，不是对生产已发生越权的断言。
