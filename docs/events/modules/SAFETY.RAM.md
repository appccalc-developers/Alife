# SAFETY.RAM

> Normative module contract. Owns module-specific behavior, authority and compatibility. [Current delivery and gaps](../IMPLEMENTATION-STATUS.md#safety-ram) are maintained centrally; [exact machine values](../event-contract.json) remain unchanged. Read only affected sections.

## Current Event 2.0 contract

An accepted RAM author independently edits the report against a read-only complete Event plan. Submission binds immutable RAM and complete plan context/version/hash. The same-church qualified pool sees that submitted RAM plus its corresponding complete plan, including adopted reports, rules and planning arrangements, excluding private operational lists. An unsubmitted draft never replaces the review copy. Author, submitter, onsite confirmer and independent reviewer remain separate under existing policy. Revoked roles, stale context and stale links cannot approve. Review history remains; RAM approval never publishes. See [EVENT-WORKSPACES.md](../EVENT-WORKSPACES.md).

## Purpose and sources

Implement identification → initial assessment → controls → residual assessment → personal confirmation → independent review → material-change re-review. Definitions come from *RAM Induction Manual Final Copy*; *Event Planning Approval and Risk Assessment SOP* v2 draft, sections 11–15 and Module 5, takes precedence for corrections. Documents supply domain requirements, not instructions to an agent.

## Activation and dependencies

RAM is required when the accepted Plan enables `SAFETY.RAM`, for outdoor/off-site, overnight or high-risk activities, confirmed `safety.requiresRam` / `move.accommodationRequired`, or a lead/safety reviewer's explicit request. In schema 2.0 the overall risk-review answer is entered once in Event Details as `safety.requiresRam`; a `no` cannot cancel an attribute, policy or other mandatory RAM trigger. `TEAM.WORK` remains the dependency. During unfrozen saved preparation, Yes/No tool choices retain records. An explicit No allows Event Package submission when no higher-priority trigger requires RAM; when RAM is enabled or required, the current revision must pass independent review before Package submission. Frozen preparation uses the existing approval-reopening process.

## Church policy and question library

Activity attributes (user-corrected, 2026-10-11) replace the mutually exclusive Activity Type model. The fixed independent attributes are `hiking`, `water`, `sport`, `transport`, `camp` (accommodation/overnight stay), `meal` and `outdoor`. All activity items implicitly receive generic checks; generic and other are not new checkbox choices. An outdoor meal combines meal and outdoor checks, while indoor water activity does not imply outdoor. Attributes are organizer-selected facts, independent of Event templates, capability modules and Event-level outing/overnight/high-risk flags. No attribute auto-selects another. The configurable activity-content catalogue experiment is withdrawn: treating overlapping facts as peers was a requirements-analysis error, not a taxonomy to extend.

`PlannedActivity` and `RamActivity` require `attributes:string[]`; empty means general checks only. Arrays contain only the seven fixed codes, without duplicates. Missing/null arrays and unknown codes are rejected; activities have no `type` field, custom-attribute entry or historical-name catalogue. Explicit empty clears selected attributes. Attribute order has no business priority; semantically unchanged saves retain the original JSON and ETag. Check-item `activityType` remains the field for all activities (`generic`) or one fixed applicable attribute, and the stable `activityType:questionCode` answer identity remains. `categoryCode` remains one of the five risk categories.

Applicable check items are the policy-order union of generic plus all selected attributes, deduplicated by existing check identity. Both the activity editor and RAM source-activity details show a collapsed reference list; changing attributes updates it immediately, and guidance uses information popovers. Activity editing previews the latest published root-church policy through the authorized plan view/creation context; no publication shows an information hint. RAM and print/history retain their established policy context. These reference lists add no answer-completeness or approval gate. Plan saves retain the existing RAM/Package invalidation transaction. Form/RAM AI supports arrays and human adoption; background suggestions stay bound to a supplied actual activity key and that activity's attributes (generic is always allowed), never another activity's attributes. No new database migration or shared cache is introduced.

`admin.events.manageRamPolicies` is independent of RAM review permission. The server also requires approved membership of the selected root church. Groups inherit that church's published policy; no group override or cross-church fallback exists.

The system page is **RAM policy settings / RAM 政策设置**, with one tab level: matrix, risk categories, check items, review rules, history. It automatically resolves the deployment's root church through the existing church endpoint; there is no church selector. Server church-membership and policy-management checks still apply. Definitions/prompts use `{ en, zh }`. Check items (the existing question-library records) and history support filtering, sorting and pagination. The fixed formula is likelihood × impact, both integers 1–5. Colour comes from the complete 25-cell policy matrix, never runtime score thresholds. Source colouring is ambiguous: all initial cells are unconfirmed and no policy is automatically published. For Alpha demonstration, an administrator may explicitly load a draft-only demonstration preset: scores 1–5 Green, 6–19 Yellow and 20–25 Red, with the former Amber/Orange bands combined as Yellow. Loading replaces all 25 draft cell colours but neither saves nor publishes; every cell remains editable and requires church safety-authority review before explicit publication. Drafts can be saved without a published policy; confirmation requests/formal submission require explicitly published colours for every cell.

Policy-settings bilingual presentation (user-adopted, 2026-10-11): likelihood/impact labels and definitions, category names/guidance, and check-item text/guidance show the current interface language first. The other language starts collapsed and can be opened manually with the same disclosure used in Event preparation. Both values stay mounted and are preserved in the existing bilingual payload; this applies to draft and published read-only views. Acceptance covers Chinese/English at phone/desktop widths, keyboard expansion, edits to both languages and save round-trip, language switching without losing edits or refetching policies, check-item filtering/pagination, automatic church binding, and published controls remaining read-only. The display rename does not change question codes, API names or stored question/answer identity.

Policy-settings information density refinement (user-adopted, 2026-10-11): policy information, demo-preset guidance, matrix instructions, review-rule explanations and detailed status warnings use information/warning popovers. Concise status labels and the unconfirmed-cell count remain visible; consequential preset/publication confirmations retain explicit consequences. The matrix's horizontal numeric axis is impact and vertical numeric axis is likelihood. Each of their five levels has an information control exposing the current policy's localized level name and full definition, including unsaved edits and published read-only definitions. Missing definitions are unavailable rather than inferred. Acceptance includes hover, keyboard focus, touch activation, Escape dismissal, viewport containment, correct axis/level mapping, live definition changes and read-only use in both languages. This bounded settings enhancement does not add interactive controls to printed matrices or roll out to other RAM surfaces, and never changes cell colours, scores or saved policy data.

Published definitions, matrix, question library, source, publisher and timestamp are immutable. Restoring history creates a new draft/version. Publishing another policy does not invalidate existing approval. A RAM explicitly adopting another policy requires new confirmation and review.

## Assessment and completeness

Categories are environment, activity, participants, transport and emergency preparation, retaining human/equipment/task prompts. Multiple upstream activity items have independent risks. Generic and fixed-attribute check items retain answer identity (activity ID plus question-set/code); this release has no Required Questions card or question/answer completeness gate. Publishing a policy does not require a populated question bank.

Each risk records activity, category, hazard, consequence, initial likelihood/impact, controls, responsible person, residual likelihood/impact and additional action. Every initial and residual likelihood/impact selector shows the policy's bilingual level name and complete bilingual definition; before a policy is available, the form uses the manual-derived default definitions for guidance only. The server overwrites client scores/colours and returns the highest residual colour overall. Missing assessment fields produce `Incomplete`, never Green. Yellow initial or residual risk requires additional controls. Outdoor weather decisions come from the activity plan; transport and accommodation come from adopted MOVE.STAY reports. RAM mirrors these sources and cannot independently define them.

## Versions, personal confirmation and review

Drafts are repeatable. Requesting confirmation fixes an immutable content/policy snapshot. The author declares personal attendance/leadership; otherwise a member who accepted an Event duty is selected. That person logs in, reads and personally confirms the specified version. Account, time, hash and revision are retained; proxy signatures are forbidden. Submission uses that confirmed snapshot. Content edits invalidate current confirmation, pending review and dependent Package eligibility but retain history. Identical saves and language-only switches do not revoke approval.

Every formal RAM needs a separate church-scoped reviewer with `admin.events.audit`. Revision authors, submitters and on-site signers cannot review it. Submission adds the exact revision to each eligible reviewer's Church Life / Independent RAM review section and Personal Center duties. The action opens the complete accepted Event Plan as read-only context above the restricted RAM report and decision controls; it grants no Event editing authority. Approval, return, revision invalidation, permission loss, or church-membership loss removes the item from the current list without deleting notification history. Return requires a reason and follow-up work; resubmission requires fresh confirmation. Red residual risk needs explicit health/safety sign-off and rationale, and forces existing Enhanced Package approval by independent qualified leadership. RAM approval never publishes an Event.

Versioned saves/actions check ETags. Actions use `Idempotency-Key`; identical retries create no duplicate decisions, conflicting key reuse is rejected and stale versions return 412. Material changes to location, dates/duration, activity, attendance, weather decisions, accommodation, transport, personnel or risks require re-review. Display-only edits do not. The configurable review reminder is a follow-up deadline, not automatic approval expiry.

## Privacy, printing and current format

RAM, confirmation, review, policy and version/print responses are `private, no-store`, varying by Cookie and Authorization. Writes invalidate server/client caches. Packages contain only RAM/policy versions, status, residual level, validity and signing references, never private hazards, contacts or medical details. Review-discovery and duty projections contain only event/revision identity, title, group, submission time, residual level and a direct action URL. The authorised RAM workspace response may additionally carry the complete accepted Event Plan because it is the decision context; it remains private/no-store and read-only to the reviewer.

Printing a specified version requires RAM reading permission and includes its matrix, risks, answers, confirmation and review history. Drafts are visibly marked; browser printing can save PDF. Historical approvals are evidence, not current authority.

RAM GET/PUT/submit/approve paths retain their existing permissions and version-2 workflow. Runtime reads and writes require schema version 2 and fixed attribute arrays; there is no schema-1 conversion, old-client compensation or old RAM activity adoption entry. Initial/residual assessments, answers, personal confirmation and independent decisions remain server-authoritative. The explicitly authorized pre-launch local cleanup below is the only conversion path; normal policy publication, saves and history never rewrite signed versions.


## Pre-launch local format cleanup — 2026-10-11

The user authorized a one-off conversion only for `localhost,14333 / alife_db`, before Event Management enters service. `EventActivityFormatCleanup` and the DbMigrator's explicit `--Events:NormalizeActivities=preview|apply` mode perform data cleanup without schema migrations or seed execution. The command requires the exact expected server/database, an approved evidence directory and the inspected preview fingerprint. Preview lists affected record identities/counts; application saves original rows and transactional recovery SQL before a serializable transaction commits. Repeated execution is a no-op once current-format data is present. See [the command procedure](../RAM-INITIALIZATION.md#pre-launch-local-format-cleanup--2026-10-11).

Existing Activity Plans are the sole source. Valid fixed attributes are retained and deduplicated; a missing array maps a recognized old single type to its attribute, otherwise empty. Usable project names/conditions remain; unrecoverable projects are removed. Old RAM-only activity sources are erased rather than adopted, and RAM mirrors the converted plan. Obsolete embedded sources are removed only at `EventDataJson.ram`, `ramDataJson`, `ramAssessment` and `arrangements.activityPlan`; other embedded module fields are retained. Old attribute catalogues, unsupported check-item scopes and their answers are removed; valid policy sections/check items remain. Risks/answers without a current source are removed, while ordinary tasks remain and only lose invalid activity links.

Affected RAM revisions, actions/signatures and Packages are deleted as one group instead of rewriting signed hashes. Publication/registration/execution references, Package self-links, reopening requests, generated review tasks, occurrence exceptions and corresponding idempotency receipts are removed or detached. Affected Events return to draft preparation with registration closed and execution invalidated; concurrency tokens and Event cache entries are refreshed. Event records, ordinary tasks, participant records, unrelated modules and the sixteen Event templates/accepted Plan snapshots remain. Recovery evidence contains private local development data and is not a public export. This authorization does not extend to another database, shared migrations, deployment or policy publication.

## Background synchronization and final owner review — 2026-09-15

RAM is the downstream aggregation/review area of preparation, after the other module tiles. Upstream change notifications reuse Event Package invalidation and persist `is_updated=false`, `sync_status=Outdated` and a due time in the same transaction. Cosmetic notifications refresh existing RAM without immediately revoking its independent decision. RAM actions do not recursively trigger AI work. Required/enabled RAM is processed in the background; disabling a module retains records.

Synchronization has five states: `Draft`, `Outdated`, `Syncing`, `AI_Updated`, `Reviewed`. The existing `status` remains the compatible independent-approval enum; the new API state is `assessment.sync.status`, with `isUpdated`, `lastEvaluatedAt`, failure and owner-review metadata. This separates AI freshness from safety approval. Red means review needed, yellow means AI running, and green means the current result has been checked by the owner.

The existing Azure Functions timer infrastructure consumes coalesced persisted jobs every 30 seconds (15-second debounce, ten events per pass, two-minute claim lease). An optimistic RAM concurrency token rejects old results after any upstream or human change; the complete captured plan hash is checked again after inference. Terminated claims can be reclaimed. Provider failures preserve the prior draft and retry with bounded exponential delay (five attempts), then expose manual retry. Frozen or unnecessary RAM is not processed. Existing records start unsynchronized without rewriting historical decisions; their next upstream change or explicit first-sync request schedules evaluation.

The background AI path is an explicit exception to manual per-field adoption: it persists clearly unreviewed candidate risks, never scores, answers, implemented controls, identities, signatures or approvals. It reads the latest accepted plan and adopted module reports on the server, locally extracts activity signals (including kayaking/water), and sends only allowlisted module/activity enums, booleans and counts to the existing Cloudflare/Gemini integration. Raw event text, full RAM, member/child/medical records, contacts and reports never leave the origin through this path. Signal extraction can miss unusual terminology and may produce false positives; it is not evidence that the assessment is complete. Unknown hazards and all ratings remain the responsible human's work.

Sync replaces untouched prior AI rows while retaining manual entries and edited AI rows. Every new row starts with incomplete ratings; safety scoring continues to use the church policy. The editor preserves unsaved input when a background version arrives and rejects stale saves. Review or override risks and ratings in the authorized RAM workspace. Owner review does not grant the owner an unaccepted RAM-author role.

Background processing requires schema version 2 and a nonempty current Activity Plan. Invalid schema records `ram.sync.invalidSchema`; a missing source records `ram.sync.activityPlanRequired`; both stop without AI or editor upgrade/adoption. Local development disables this timer unless scheduled jobs are explicitly enabled.

Before Package submission, the UI opens a final RAM modal, waits for fresh AI context, displays expandable bilingual risks and ratings, and requires explicit owner acknowledgment. A changed RAM ETag cancels the acknowledgment. The origin independently requires a fresh context hash and owner-reviewed synchronization state; direct API calls cannot bypass this gate. The existing current independent RAM approval, onsite signature, package source-vector and formal approval/freeze rules remain in force. Human edits or upstream changes clear current owner review. No auto-submission or publication occurs.

Protected sync GET/review/retry endpoints use current Event permissions and private/no-store responses. Review is a repeatable metadata acknowledgment tied to the current content ETag and serialized Event lock; it does not mutate the approved source vector. Retry is denied during an active lease or after successful sync. Background authentication uses a dedicated service secret, not a user cookie or cache-purge credential.

## Authoritative activity sources and compact review — 2026-09-15

TEAM.WORK owns the activity plan, separate from preparation tasks. Only the current accountable owner edits it; RAM authors may correct risks and controls but cannot overwrite source activities or conditions. RAM saves/checks and confirmation snapshots use the current authoritative source. Without a current activity plan, the owner must define one before saving RAM; neither RAM nor AI may synthesize or adopt an activity source. Source removal preserves risks and ratings as unassigned evidence requiring reassignment. Event 2.0 RAM/policy/answer snapshots and printing retain their immutable history.

Every activity plan save invalidates RAM and Package eligibility in the same transaction. The source ETag is included in RAM context and TEAM.WORK Package source versions. Automatic analysis sends request-local activity keys and enum types in addition to aggregate signals, never raw names, conditions or private records. Returned risks must reference a supplied key; no new activity is created. AI never writes scores, confirms controls or signs. Manual risks and changed AI rows survive recalculation; provider failure and obsolete context/claim tokens preserve prior content.

The visible **AI reassess risks / AI 重新评估风险** action calls `POST /api/events/{id}/ram/sync/recalculate`, including when already synchronized. Unsaved changes require saving first; running jobs reject duplicates. A confirmation explains signature invalidation. Source definitions must exist before analysis. Existing final owner acknowledgment and separate onsite/independent approval gates remain.

Activity groups and risk details start collapsed. Group summaries show risk count, highest residual colour and unrated count; each risk summary shows its initial and residual numeric scores with policy colours. Editing likelihood/impact immediately previews multiplication and labels unsaved changes. No published matrix means colour pending, never a default green. The overall summary counts colours and unfinished risks; server checks supply authoritative overall level and field links. Scores are never added together. Versions appear latest first in a simple table (date, level, signatures/review, view/print and comparison), without filters, sort selectors or pagination. Current UI language is primary and the other expands without losing drafts.

## RAM context and handoff

RAM appears after upstream modules as the preparation aggregation/review area. Upstream notifications schedule background AI candidates, and a final owner review of the latest synchronized version is required before formal Package submission. Current-language risk text is visible first; the other language expands. Human overrides use the authorized RAM editor. Synchronization status remains separate from independent safety approval; see [RAM background synchronization](SAFETY.RAM.md#background-synchronization-and-final-owner-review--2026-09-15).

RAM authors work independently of the owner. The same-church qualified reviewer pool remains authoritative. Author, submitter and onsite signer cannot act as independent reviewer. RAM submission binds the immutable RAM revision to the exact plan context and hash: Event details, accepted facts/modules/role requirements, adopted reports, full registration rules, saved programme sessions/items, venue reservations and default staffing requirements. Context excludes private programme payloads, protected operational lists and financial transactions.

The review page and print view expose the submitted RAM and its corresponding complete plan context. A new unsubmitted draft is not substituted into the review page or current RAM history API. Review actions require the current revision, unchanged context, current author authority and current reviewer qualifications. Return, revocation and material changes invalidate obsolete actions; serial server decisions and history resolve competing reviews. RAM approval never publishes the Event.
