# Event design provenance and orientation

## Current authority

[Core contract](EVENT-CONTRACT.md), delegated topics/modules and [machine JSON](event-contract.json) own current Event rules. [Status](IMPLEMENTATION-STATUS.md) owns supported scope; historical logs own dated evidence. The current generator projects these sources into the existing explanation and handbook HTML.

Repository inspection on 2026-10-01 found four fixed archetypes and sixteen initial Activity Types in composition and machine definitions. Runtime administrator-created templates can make the database catalogue larger; no live catalogue count was queried. The twelve capability definitions do not imply all twelve have operational support: status marks partial and unavailable modules separately.

## Original YAML and EMBOK

The user's original YAML/EMBOK design is an important provenance requirement. Focused searches of current Event documentation/application sources and repository YAML filenames did not locate an Event YAML authority or an EMBOK source. YAML presently located includes CI/configuration and image OpenAPI, which must not be relabelled Event workflow design. Absence from this search does not prove original inputs never existed.

Pending provenance work: locate the original source or historical attachment, identify its version, map its functional and nonfunctional requirements to current contracts, and record adopted/changed/deferred decisions. Do not invent EMBOK compliance, silently convert JSON to YAML, claim forty-six current types, or reactivate retired generic workflow behavior without evidence/authorization.

## Implementation orientation

Use the [reading matrix](AGENTS.md). Composition proposes; explicit human acceptance creates the immutable Plan; organizational approval and explicit publication remain distinct. Role assignments, policy evidence and module permissions are independently authoritative. Current stages are preparation, registration, execution and followup; preparation is nonlinear. Legacy generic workflow fields may remain readable but are not a new orchestration engine.

The engineering orchestration is the requirement-to-evidence loop in [common design](../design/README.md); product Event orchestration follows its own contracts. Keep those meanings separate.

## Explanation and prototypes

Reuse [EventManagement-About](EventManagement-About.html) and the generated handbook through their generator; do not edit generated HTML. Existing design reference images are bounded historical pilot evidence. Their adoption does not establish current full rollout. New demonstrable prototypes must show supported actions, denied/blocked states and simulated data clearly, retaining source and user-acceptance scope.
