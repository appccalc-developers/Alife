# Event 2.0 instance reset boundary

> The former protected production reset, rollback and finalize workflows are retired. This page records the Event-only boundary, the local rehearsal and the separately authorised one-time production operation. Product rules remain in [the Event core contract](EVENT-CONTRACT.md); exact runtime rules remain in [event-contract.json](event-contract.json).

## Boundary

The pre-launch compatibility exception covers Event instances and Event-scoped operational data only. Accounts, churches, groups, pages, sermons, albums, Event template versions, RAM/Package/safeguarding policy versions, workflow templates, venue resources and all other non-Event data remain outside it. `EventDataJson` remains the Event business carrier.

Composition `2.0.0` accepts no Event 1.x payloads. Project questionnaires require `questionnaireVersion: 2`; RAM retains its independent `schemaVersion: 2`. From 2.0 onward, Plan, RAM, Package, registration, fee, consent, task and venue histories again require compatible evolution and immutable audit history.

## Explicit reset utility

`Alife.DbMigrator --Events:PurgeInstances=preview|apply|verify` is an explicit utility that exits before ordinary migration, seed, sermon normalization or unrelated cache work. `preview` checks known SQL metadata and references and records a target-bound fingerprint. `apply` checks the same target, code, schema, freeze epoch and approved preview fingerprint before a serializable, application-locked delete. `verify` checks Event-scoped rows and references are empty and preserved data is unchanged. The recoverable local mode still requires verified backup references.

For this one-time, user-authorised production purge, the additional exact argument `--Events:NoRecovery=true` selects an irreversible mode. The mode is production-only, rejects backup claims, binds the absence of recovery to the preview fingerprint and apply receipt, and refuses to commit if the manifest contains an Event-exclusive remote file requiring deletion. It does not loosen the explicit target, frozen-write, manifest, count or preserved-data checks. A discovered exclusive object blocks this mode until its handling is separately resolved; shared files and non-Event objects must not be deleted.

## Isolated Event 2.0 storage migration

The ordinary DbMigrator also seeds and normalizes non-Event data and invalidates caches. The one-time `Alife.DbMigrator --Events:Event2MigrationOnly=apply-prerequisite|apply|verify` entry point exits before those ordinary steps. Each mode requires the exact reviewed production Azure SQL target; mutation modes also require confirmed frozen Event writes. Read-only preflight uses `--Events:Event2MigrationGate=inspect`; the migration-only command has no `preview` mode.

The exact production migration chain was `20261011113522_AddEventProjectOperations`, then `20261012225333_Event2RemoveLegacyEventStorage`. `apply-prerequisite` accepts only that order and an empty `legacy-67` Event schema, applies only the first migration, then verifies the `legacy-75` schema, its project-operations tables and the remaining sole pending Event 2.0 migration. `apply` accepts only the latter as pending and an empty `legacy-75` Event schema, applies it, and verifies retired tables/columns are absent while preserved tables and migration history remain. `verify` repeats the post-migration checks without mutation. This is a gated 67→75→2.0 sequence; the command never purges Event instances and does not run non-Event seed, sermon normalization or cache steps. Both production commands and the separate read-only verify succeeded while API Event writes remained frozen; logs are under `C:/Data/Alife/Temp/Event2ProdNoRecovery20261014/event2-prerequisite-migration.log`, `event2-migration-only.log` and `event2-migration-verify.log`.

## Ordinary API deployment boundary

The checked-in `migrate-and-deploy` workflow performs read-only, exact-target identity and Event 2.0 migration inspections with `--no-launch-profile` before changing the database or deploying the API. If the Event 2.0 migration is pending, deployment stops; there is no ordinary-deployment switch that can apply the destructive migration. The workflow requires the Function App to already hold a current `EVENT_DATA_EPOCH` other than `pre-event-2-reset` and an explicit `EVENT_WRITE_MODE` of `open` or `frozen`. It preserves those values and does not silently select a pre-reset epoch or open writes. The retired protected Event release environment is no longer part of this workflow; its Azure OIDC login uses the already configured repository `main`-ref federated subject and repository secrets. These are checked-in deployment guards, not evidence that a new workflow run has completed.
