# Event 2.0 destructive reset

> Normative operational contract for the one authorised pre-launch Event reset. Product rules remain in [the Event core contract](EVENT-CONTRACT.md); exact wire rules remain in [event-contract.json](event-contract.json).

## Boundary

The reset deletes every Event instance and all Event-scoped operational data. It preserves accounts, churches, groups, pages, sermons, albums and other non-Event domains. It also preserves Event template versions, RAM/Package/safeguarding policy versions, workflow templates and venue resources. `EventDataJson` remains the current Event business carrier after the cutover.

The reset is the only exception to Event backward compatibility. Composition `2.0.0` accepts no Event 1.x versions. Project questionnaires require `questionnaireVersion: 2`; RAM retains its independent `schemaVersion: 2`. From 2.0 onward, Plan, RAM, Package, registration, fee, consent, task and venue histories are immutable and require normal compatible evolution.

## Dedicated command

`Alife.DbMigrator --Events:PurgeInstances=preview|apply|verify` runs before ordinary migration and seed logic and exits after the selected operation. The purge mode must never run migrations, seed data, sermon normalization or unrelated cache work.

`preview` reads migration history and live SQL metadata, validates the known optional-table model and fails closed for unknown Event tables, foreign keys, malformed soft references or unexplained orphans. Its protected evidence package records target identity, code SHA, freeze epoch, schema and migration hashes, Event/occurrence/project identifiers, per-table counts, soft references, exact file-object candidates, preserved-data counts and stable hashes, plus one total fingerprint. Workflow evidence is encrypted and accompanied by an HMAC-SHA256 sidecar that is verified before decryption. Ordinary logs expose counts and hashes only.

`apply` requires the same code SHA, server, database, schema hash, freeze epoch, verified recovery reference and approved preview fingerprint. It acquires `sp_getapplock`, starts a `SERIALIZABLE` transaction, recomputes the fingerprint and aborts on any difference. It breaks approved self-reference cycles and deletes in explicit reverse-FK order. Expected and actual row counts must match before commit.

`verify` requires all Event instance tables and Event-scoped soft references to be empty, Event-scoped idempotency data to be empty, preserved definitions/resources and non-Event stable hashes to match the preview, and the remote file failure list to be empty. A repeated preview/apply must produce an empty change set.

## File and cache handling

File handling uses a signed exact-key manifest. Before SQL apply, Event-exclusive objects are copied to a private recovery area that the normal application identity cannot read. Shared `FileAsset` rows or shared object keys only lose their Event association. After SQL commit, only manifest-listed source keys are deleted; prefix-recursive deletion is forbidden.

Before publishing the protected production preparation release, create the separate **non-public** R2 bucket `ccalc-event-reset-recovery` and bind it as `EVENT_RESET_RECOVERY_BUCKET` to the Images Worker. The protected preparation workflow may create this exact bucket idempotently, then must prove its managed and custom public domains are disabled before deploying the Images Worker. The source bucket remains `ccalc`; the recovery bucket must not be publicly served or readable through ordinary application credentials. Configure four pairwise distinct file-reset secrets, each at least 32 characters: `EVENT_RESET_FILE_API_TOKEN`, `EVENT_RESET_FILE_SIGNING_SECRET`, `EVENT_RESET_FILE_FINALIZE_TOKEN` and `EVENT_RESET_FILE_FINALIZE_SIGNING_SECRET`. Also configure the dedicated Speed Layer secret `EVENT_RESET_DO_TOKEN` with at least 32 characters; it must not reuse the ordinary cache-sync token or a file-reset secret. The authenticated Speed Layer reset-status endpoint uses the existing `CACHE_SYNC_API_TOKEN`; the protected Durable Object maintenance endpoint separately requires `EVENT_RESET_DO_TOKEN`. Ordinary Workers Builds do not require or gain access to the maintenance credential. The controlled deployment config declares it as required, and the protected workflow uploads it alongside the reviewed Worker artifact. Missing, short or incorrectly shared secrets, or an absent recovery binding, fail closed.

Every manifest object key is an exact UTF-8 key of at most 1,024 bytes and 1,024 characters, without a leading/trailing slash, backslash, ASCII control character, empty path component, `.` or `..` component. Characters such as `?`, `*`, `[` and `]` are valid literal R2 key characters and are never interpreted as patterns. Source keys cannot begin `quarantine/`; recovery keys must begin `quarantine/event-reset/`. The derived `.metadata.json` sidecar key must independently satisfy the same limit and path rules. Each recovery object and sidecar is written to the private bucket with verified body/metadata hashes and the approved reset binding. A key that cannot carry its sidecar is a preview/backup blocker, not a reason to truncate a key or skip evidence.

Public and generic Images Worker reads and listings reject `private/` and `quarantine/`. Maintenance copy, quarantine and delete operations accept only the protected manifest and exact keys. Failures remain in the manifest for retry and make verify fail.

After commit, clear Event HybridCache, Cloudflare KV and the current PoP Cache API entries, including public upcoming, group Event, registration and approval views. `EVENT_DATA_EPOCH` is the persistent reset boundary: it scopes backend HybridCache keys, Speed Layer Cache API/KV/logical Event keys and Durable Object names, equals the approved reset epoch during the reset, and remains set after the write freeze is removed. A missing or mismatched production data epoch fails closed. Known old browser draft keys are deleted; drafts, pre-epoch cache entries and transient sessions are intentionally not restored.

## Durable Object session reset

The Speed Layer retains the three Event-only Durable Object namespaces and class names: `EVENT_SESSIONS` / `EventPlanningSession`, `ENROLLMENT_SESSIONS` / `EnrollmentSession` and `REVIEW_SESSIONS` / `ReviewSession`. `EnrollmentSession` is retained only so the protected reset can discover and clear pre-reset storage; it has no product session route and cannot create a new enrollment session. Current public AI session routes use only `EventPlanningSession` for the Event Details Assistant and `ReviewSession` for Event review.

A Worker version upload cannot apply a Durable Object lifecycle migration. The reset therefore does not delete or recreate any of these classes and ordinary version uploads contain no pending class lifecycle change. During protected preview, the workflow inventories every object in all three exact namespaces and creates the protected Durable Object manifest and fingerprint. Inventory accepts only the expected Cloudflare account, the `app-ccalc` Worker, the exact class-to-binding mapping above, one SQLite namespace ID per class and no unexpected namespace owned by that Worker. Ordinary logs contain only class-level counts and hashes; object IDs remain inside encrypted evidence.

The maintenance endpoint is an internal path on the publicly reachable Worker router. It is usable only while the production Event runtime is frozen at the matching schema, reset and data epochs. Each request must use the dedicated `EVENT_RESET_DO_TOKEN`, include `X-Alife-Event-Reset-DO-Signature` with an HMAC-SHA256 signature over the exact raw JSON body, and carry the fingerprint currently deployed as the temporary `EVENT_RESET_DO_APPROVED_FINGERPRINT` Worker variable. The endpoint also checks the approved manifest metadata, class-to-binding pair, namespace ID and batch hash before resolving an object. The ordinary `CACHE_SYNC_API_TOKEN` cannot authorize this operation.

Protected apply clears every manifest-listed object by deleting its alarm and calling `storage.deleteAll()`. Receipts are bound to the approved manifest and fingerprint. If a run stops after some batches, the same approved manifest can resume: already empty listed objects remain successful, outstanding listed objects are cleared, and a changed namespace identity, an object outside the approved manifest, a failed receipt or remaining stored data blocks completion. Verify re-lists all three namespaces, rejects any object identity outside the approved manifest, and requires every remaining approved identity to report `hasStoredData: false` before unfreeze. The persistent data epoch still prevents a pre-reset browser or stale client from addressing a new Event session after the clear.

## Production sequence and recovery

Production runs only from the dedicated manually dispatched workflow bound to the protected `production-event-reset` environment, required reviewers, fixed target variables, minimum-privilege identities and single-run concurrency. Ordinary deployment, Terraform, application startup and normal DbMigrator execution cannot start the reset.

1. Run `production-event-preparation-release` from the exact reviewed legacy-preserving preparation SHA on its protected branch. It verifies the live legacy schema, exact Azure SQL and Function App target, protected source connection and available non-public R2 recovery bucket; deploys and attests the Images Worker safeguards; then deploys the preparation backend without migration, seed or reset and records its verified SHA and run ID. The release removes Event seeding, supports a shared write-freeze epoch, exposes safe maintenance status, and contains the reset command. Confirm the four file-reset secrets and dedicated Durable Object reset secret above before running the workflow. The named SQL recovery copy is created only after the write freeze, not as a prerequisite to preparation.
2. Bind the running Function App connection, protected reset connection, named Azure SQL resource and live backend database probe to one normalized SHA-256 target identity; any mismatch or missing probe blocks the run without logging connection details. Freeze Event writes across every writer. New writes return `503` with `Retry-After`; wait for in-flight work to drain. After the backend reports the same target identity, zero active mutations and scheduled-job acknowledgement, stop the Azure Function App and prove every instance is `Stopped` for the protected SQL phase; immediately before SQL apply, read the stopped app configuration again and require the same identity. Speed Layer and Images remain frozen.
3. Preview alone creates the named transaction-consistent Azure SQL copy, using the reviewed full destination resource ID, only after every Event writer is frozen and the Function App is stopped. The copy is tagged with the reset run ID, freeze epoch, code SHA, source identity hash and preview workflow run ID. A retry may reuse a copy only when every tag matches; apply and verify require the original preview run ID and never create a replacement. Verify destination connection identity, Online state, migration history, counts and hashes against the still-frozen source. Copy exact Event-exclusive objects to private R2 recovery storage and verify each object.
4. Run production preview, review its protected SQL/file and Durable Object manifests, and approve both fingerprints through the protected environment. The frozen Speed Layer artifact receives the approved Durable Object fingerprint as the temporary `EVENT_RESET_DO_APPROVED_FINGERPRINT` variable.
5. Run apply and verify, clear every approved Event-only Durable Object instance, delete exact manifest-listed source objects and clear caches at the approved persistent data epoch. A retry resumes from the same approved manifests and receipts rather than generating a broader deletion scope. Durable Object verify must report no stored data in any of the three validated Event-only namespaces. An `always()` recovery step restarts the Function App in frozen mode after the protected SQL phase, including an intermediate failure, and verifies the schema, reset and data epochs before successful reset evidence can be recorded.
6. While still frozen, publish the final 2.0 runtime and forward migration. Verify rejected 1.x requests, removed routes and a side-effect-free current-template composition dry run, then unfreeze.

The SQL copy, R2 recovery objects and signed manifest remain for 30 complete days. A separately protected finalize operation identifies the original run, verifies production health and absence of a rollback hold, then removes only those recovery assets. Rollback freezes writes again, restores the copy into a new database, verifies it, switches the connection, and restores R2 keys from the manifest; it never overwrites the current production database in place.
