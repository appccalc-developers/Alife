# Frontend Architecture

## Purpose

The Alife frontend is a React PWA for members, group leaders, co-leaders, admins, and guests. It provides the mobile-first user experience for group discovery, member workflows, bilingual pages, sermons, events, enrollments, reviews, notifications, image uploads, and AI-assisted workflows.

The frontend should stay focused on presentation, interaction, client-side coordination, and optimistic user experience. Authentication, authorization, persistence, and shared cache correctness remain backend and speed-layer responsibilities.

## Application Shell

`src/main.tsx` wires the top-level providers:

```text
React StrictMode
  -> QueryClientProvider
  -> AuthProvider
  -> CurrentGroupProvider
  -> BrowserRouter
  -> App
```

`registerServiceWorker()` is called during startup so production builds can install the PWA service worker generated by Vite.

`App.tsx` owns the route tree, app shell, navigation, context drawer, and floating actions. Route-level screens live under `src/views/`.

## State Model

### AuthProvider

`src/stores/auth.tsx` owns:

- Current member profile from `GET /api/me`.
- Bootstrap state.
- Local language selection.
- Guest/registered/admin flags.
- Membership list.
- Convenience role checks such as `canManageGroup`.

Language is stored in local storage under `alife.language`. Changing language should not refetch server data unless the underlying data changed.

### CurrentGroupProvider

`src/stores/currentGroup.tsx` keeps active group context stable across app navigation. This helps member-facing and leader-facing screens share the same selected group without unnecessary remounting or refetching.

### Leader UI Preferences

`src/stores/leaderUiPreferences.ts` stores management UI preferences. Keep this local and presentation-focused.

## Query And Cache Strategy

The frontend uses three client-side data tools with separate responsibilities:

### TanStack Query

TanStack Query coordinates server state reads, mutation invalidation, loading states, and error states.

Use it for normal API-backed screen data and mutation lifecycle coordination.

### TanStack React DB

React DB collections under `src/db/collections/` support local list-style data coordination for groups, pages, and sermons.

Use collections when the feature benefits from normalized local list data and predictable list updates.

### IndexedDB ETag Cache

`src/db/httpCache.ts` implements `conditionalGet`:

```text
read cached data and ETag from IndexedDB
  -> send If-None-Match
  -> if 304, return cached data
  -> if 200 with ETag, parse and store new data
```

This works with speed-layer generated ETags and avoids unnecessary payload downloads while still respecting authorization and cache validation.

Do not use the PWA service worker to replay `/api/*` responses. API data is handled by HTTP validation and app-level caches.

## PWA Architecture

`vite-plugin-pwa` generates the service worker during build. `src/registerSW.ts` registers it when the browser supports service workers.

The PWA cache strategy is intentionally limited:

- Cache built shell assets.
- Cache same-origin images and fonts where safe.
- Cache supported external image URLs where configured.
- Do not runtime-cache `/api/*` responses.

This protects users from stale private data after logout, membership changes, or permission changes.

See `docs/pwa.md` for PWA-specific behavior and iOS notes.

## Routing And Active Entity Context

`src/services/activeEntityService.ts`, `src/hooks/useActiveEntityIds.ts`, and group route utilities keep active group/page/event context stable across canonical and parameterized routes.

This matters because Alife has both:

- Member reading routes.
- Leader management routes.

Keep route state explicit. Avoid making language switches, tab changes, or local editor changes trigger unnecessary server refetches.

## Bilingual Content

Alife supports English and Chinese. Content fields often use:

```json
{
  "en": "English text",
  "zh": "Chinese text"
}
```

Frontend helpers:

- `utils/localizedText.ts`
- `utils/bilingualValidation.ts`
- `utils/pageBilingualCompletion.ts`
- `i18n/uiText.ts`

Guidelines:

- Preserve bilingual structures already returned by the API.
- Keep UI translation separate from stored content translation.
- Do not convert localized objects into plain strings.
- Do not refetch API data merely because the user changes display language.
- Use translation AI helpers only as user-reviewable assistance.

## Page Builder

The page builder is section-based. It does not treat pages as raw HTML blobs.

Important areas:

- `PageEditorView`
- `components/page-editor/`
- `components/page-sections/`
- `components/page/PageContentRenderer.tsx`
- `utils/pageSectionContent.ts`
- `utils/listViewMetadata.ts`

Pages have bilingual metadata and ordered sections. Sections have explicit types and JSON content/style payloads.

When changing page builder behavior:

- Keep saved page JSON migration-friendly.
- Support preview and published rendering separately where needed.
- Preserve existing section type behavior.
- Keep editor flows understandable for non-technical group leaders.
- Avoid hidden schema changes.

## Group And Member UX

Group reading and group management are intentionally separate:

- `GroupDetailView` is optimized for normal member browsing.
- `GroupManageView` is optimized for leader/co-leader operations.

Management UI should stay task-focused:

- Member approval/rejection.
- Invite flows.
- Subgroup creation and co-leader claim.
- Page management.
- Event management.

Frontend role checks improve navigation and display, but backend authorization remains required for every protected operation.

## Events And AI-Assisted Workflows

Event-related flows include:

- Event planning and creation.
- Enrollment.
- Review/reflection.

AI session services communicate with the speed-layer Durable Object routes:

- `/api/events/session/*`
- `/api/enrollments/session/*`
- `/api/reviews/session/*`

The AI session should produce drafts and structured suggestions. The user must review and commit final data through backend REST APIs.

Do not automatically publish or persist AI-generated content without user confirmation.

## Image Handling

Image workflows use the Cloudflare image API and upload components:

- `services/imageWorkerApi.ts`
- `services/cloudflareImageService.ts`
- `components/ImageUpload/`
- `components/CoverImage.tsx`
- `hooks/useImageUpload.ts`
- `hooks/useImagePreloader.ts`

Use real `<img>` elements or existing image components for meaningful content images that need alt text, loading behavior, or responsive treatment. Use CSS background images only for decorative layout effects.

Avoid layout shift by preserving known aspect ratios or stable image container dimensions.

## Environment And API Base URL

For local development, the Vite dev server should proxy same-origin API calls to the local backend. Prefer leaving `VITE_API_BASE_URL` empty for local development.

For production builds that call a separate API origin directly:

```env
VITE_API_BASE_URL=https://api.example.com
```

The deployed normal path is same-origin through the Cloudflare speed layer.

## Change Guidelines

When changing frontend behavior:

- Preserve current React, Vite, Tailwind, TanStack, and PWA conventions.
- Keep screens responsive and mobile-friendly.
- Use clear loading, empty, and error states.
- Keep language switching local and cheap.
- Avoid unnecessary remounts and refetches.
- Keep API DTO normalization in services/utils, not scattered through components.
- Do not rely on frontend checks for authorization.
- Do not add a new state management library or UI framework without explicit approval.
