# Alife 项目交付治理

建立日期：2026-10-10。治理对象是 Alife 项目的持续交付；新系统生成插件是独立交付物。它们共享能力基线和验收方法，不共享用户数据或部署资源。

## 目标与权威

目标是让真实成员和负责人能够完成完整、可靠的工作流程，并让下一位维护者能解释、验证和继续交付。功能数量、文档数量、编译通过和历史测试数量不代表完成。

[AGENTS.md](../../AGENTS.md) 管理代理行为和操作权限；[架构](../architecture.md) 管理系统边界；[设计入口](../design/README.md) 定位业务契约；[QA](../design/QA.md) 管理验收证据。[工作台账](work-register.json) 只管理任务、优先级、依赖和证据，不重复业务规则。Event 的细分交付状态继续由 [Event 状态](../events/IMPLEMENTATION-STATUS.md) 管理，按 [Event 阅读矩阵](../events/AGENTS.md) 工作。

当前 Alife 保持 Azure + Cloudflare 架构。用户已选择让**新系统插件**提供 Azure + Cloudflare / 纯 Cloudflare 两条路线；这不授权迁移现有 Alife。

文档使用范围见 [逐文件清单](DOCUMENT-USAGE.zh-CN.md) 和 [机器记录](document-register.json)。原有 196 个 Docs 文件中，97 个保留（其中虚拟教会计划仅保留固定源版本引用，当前 main 尚无对应文档或功能），99 个移入 [待确认历史区](../../archive/pending-docs-review/2026-10-10/README.md)；尚未删除或永久确认归档。审查后新增的 Event 创建卡片设计另行登记，不改写原始审计分母。历史资料不作为当前开发或新系统生成输入；只有明确的追溯调查才按需要读取。仍有效的旧意图必须先与当前契约归整，不能直接重启历史任务。

## “完成”的边界

每个交付批次记录范围、适用契约及需求 ID、用户和角色、验收场景、证据环境、已知缺口。初始范围以当前契约为准；在 GOV-01 中核对源代码、契约和历史目标，产生可审查的发布范围。不得把历史提案自动当作当前需求，或把未完成模块悄悄移出范围。

项目完成必须同时满足：

1. 已确认范围内，每项需求都有可达的用户流程、适用的真实持久化和服务端权限检查；每项任务都完成，或有用户明确接受的延期决定。
2. 身份、成员、工作区、内容发布、Event、社区阅读与管理等完整用户旅程通过当前版本验收；角色拒绝、跨群组隔离、撤权后的访问、缓存更新、旧 JSON 和双语行为按风险验证。
3. 没有未解决的严重安全、隐私、数据丢失或范围内关键流程缺陷。证据缺口与失败分开记录。
4. 目标环境的配置、备份恢复、运维和交接经过验证；外部服务与发布仍需相应授权。无法访问目标环境时，只能声明本地完成或阻塞，不能声明项目全部完成。
5. 用户确认产品范围和产品验收。Codex 可自主完成已授权的本地实现与修复；产品决策、架构变更和发布遵循已有权限规则。

初始台账中的功能项是**待审计**，不是判定现有功能未实现。暂不输出“项目完成百分比”；需求拆分和证据基线完成后才有合理分母。

## 选题与推进

同一时间推进一个主要工作包。用户当前指令优先；在授权的持续推进范围内，先处理已证实的安全/隐私/数据完整性问题，再修复阻碍真实用户流程的缺陷，再补充交付缺口，最后做非必要优化。不要为治理而重写正常模块。

选题顺序：检查未提交变更 → 找到用户指定任务或依赖已满足的最高优先级任务 → 只读对应契约和实现 → 将任务拆成可独立验收的工作包 → 记录完成条件和风险 → 实现、验证、复核、更新台账。多个任务同级时，优先解除下游阻塞、改善真实用户价值且能小步验收的任务。

发现新的重大缺陷，先记录复现、影响和证据，再调整队列；没有证据的猜测进入待调查项。需要产品决定时，提出具体选项，继续不依赖决定的工作。阻塞不能通过降低验收标准、绕过鉴权或虚构成功解决。

本文件不会让 Codex 在聊天结束后自行持续运行。用户请求后续自动推进或定时检查时，再配置自动化及授权范围；未请求时不创建后台任务。当前聊天继续工作和未来自动运行是不同的执行范围。

## 工作包与状态

台账中的每个任务保留以下信息；复杂功能在所属领域文档拆分需求，台账引用而不复制：

| 字段 | 作用 |
| --- | --- |
| id / title / priority | 稳定编号、用户价值和顺序；P0 严重保护性缺陷，P1 交付基础与关键流程，P2 其余范围内缺口 |
| dependsOn / owners | 前置任务及权威契约路径；owners 指文档来源，不是虚构人员 |
| status | planned、ready、in_progress、blocked、done、deferred；延期必须记录用户决定 |
| acceptance | 可观察的完成条件，必要时链接细分需求 ID |
| evidence | 日期、源版本/工作树、工具与结果、环境、限制；失败也要记录 |
| nextAction / blockers | 下一步可执行动作和真实阻塞 |

实现状态（unassessed/unimplemented/partial/implemented）与验证状态（unverified/partial/verified）分别保留。planned 可以已经有实现；implemented 不能自动变成 verified。done 要有对应验收证据，不是所有命令成功就算完成。重开任务时保留旧证据并说明失效范围。

每项新证据至少记录：`date, source, environment, check, outcome, limitations`。本地测试、模拟浏览器、真实浏览器/账号、数据库、外部服务与部署证据分别标明。原有结果只作历史参考。工作台账允许数组扩展，不在没有依据时捏造全部需求条目。

## 两条交付线

**Alife 完成交付**：GOV-01 建立范围与证据基线 → 按身份/隔离优先核对完整旅程 → 修复和补全已确认范围 → 在授权环境完成综合验收与交接。初始审计只定位缺口，不一次重做全部功能。

**可复用插件**：GEN-01 创建问答、架构路线、能力基线、治理与计划生成 → GEN-02 从指定 Alife 版本提炼无租户数据的 Azure 参考实现，并验证改名后的新实例 → GEN-03 完成纯 Cloudflare 实现及同一套契约验收 → GEN-04 在目标 Codex 中安装演练、生成新项目和验证后发布。

两条路线的“功能一致”需要三个明确基准：指定 Alife 源版本的实际行为、契约中的目标行为、当前版本的验证证据。Alife 的 partial/target 模块不能被生成器宣传为已完成能力。生成器可继续实现它们，但必须单独登记和验收。

插件源位于 [plugins/alife-system-factory](../../plugins/alife-system-factory/plugin.json)。0.1.0 提供规划生成器和 Codex 实施工作流；不包含完整应用模板，也未验证可以独立生成并运行两个完整系统。该限制由 GEN-02/03/04 明确跟踪。

## 变更和收尾

新提议只登记一次：写明问题、需求来源、影响范围、验收和优先级。跨层或技术变更先形成决策记录：现状、选项、取舍、授权、兼容/迁移/回退及验证；业务权威文档仍是唯一规则来源。

每个工作包收尾检查实际 diff、对应验收、文档影响和当前证据，更新下一步。报告变更、验证、未验证项和风险。Git、Issue、PR、部署及共享迁移不因进入台账而获授权。
