# ALIFE 设计文档与 AI orientation 补齐方案

状态：实施方案，待逐领域补齐；不是产品行为变更或完成声明。

## 目标与范围

以设计和原型驱动交付，让初始功能、架构、UI/UX 与质量要求持续约束代码生成。覆盖四类功能设计：三层架构；页面制作与发布；身份、workspace 与教会/小组管理；Event Management。UI/UX 与 QA 是全部领域共同遵守的非功能要求。

本方案不授权架构替换、权限变化、生产迁移、Git 发布或新增依赖。当前行为、目标设计、待决策事项与验证结果必须分别记录。

## 已核实的基础与差异

- 总体与分层架构已有 `architecture.md`、`backend_architecture.md`、`speed-layer_architecture.md`、`frontend_architecture.md`；前端目录内 `ARCHITECTURE.md` 描述当前代码组织。
- 总体/前端文档仍列出不存在的 `src/api`，与目录内禁止新增平行 API 目录的规则不一致；`App.tsx` 当前仅导出 `app/AppShell`。
- 总体后端分层箭头没有区分层次与实际项目引用方向；必须修正。
- Event 已有核心、主题、机器契约、状态、历史、设计参考与 HTML 生成检查；沿用其权威分工，不复制其全部业务规则。
- Event 当前契约记录四个固定 archetype、十六个系统预置 Activity Type、十二个 capability module。运行时管理员新增模板的实际总量需要另行核实，不能从源码推断。
- 当前 Event 的精确机器契约是 JSON，未找到 Event YAML 权威定义。用户所说 YAML 与 EMBOK 原始设计的来源、转换链和覆盖范围需要定向追溯。不能直接改写为“完全基于 YAML”，也不能未经授权转换现有格式。

## 文档权威与入口

建立一个总体设计入口，引用现有权威来源。总体入口负责产品范围、领域地图、跨领域原则及决策状态；各领域契约负责具体业务；机器契约负责精确代码和接口；设计规范负责体验；实现状态负责交付事实；历史负责有日期的证据。HTML 是说明投影，原型是体验证据，均不能覆盖契约。

保留现有文档，优先修正和归位，避免重复创建同一规则。冲突必须明确作用域、版本和决策依据；不得把较新的实现描述自动当作设计授权。

## AI orientation 与实施闭环

每个领域提供短入口，明确适用任务、必读来源、术语、核心不变量、实现位置、允许自主操作、需决策边界与完成条件。通过仓库 AGENTS 和相关技能按任务路由，不要求每次读取所有文档。

每项任务形成“需求 → 契约 → 原型/参考 → 实现 → 验收 → 当前证据 → 缺口”的连接。先给关键需求稳定 ID，避免给每句说明强制编号。状态至少区分未实现、部分实现、已实现，以及未验证、部分验证、已验证。

实现前列适用要求和验收；实现后审查差异、执行适用检查并同步状态。证据记录源码版本或明确工作树范围、命令、环境、日期与限制。历史测试、模拟 API 和已采用的设计方向不能被当作当前生产验证。

## 非功能设计：UI/UX 与 QA

UI/UX 总体规范说明视觉语言、信息层级、导航、表单、反馈、响应式、无障碍、双语、加载/空/错误/禁用/冲突状态与偏好持久化。公共页面、一般 workspace、Event 的局部风格分别规定作用域，沿用现有设计技能和 Event tokens。区分产品统一标准、设计者偏好与用户可设置偏好。

QA 规定按风险选择检查：契约/schema 兼容、角色正反例、跨用户缓存隔离、失效、并发/重试、持久化、双语、手机与桌面交互、可访问性及构建。模型不得以编译通过替代功能或视觉验收。可机器检查的规则进入检查脚本/CI；审美与产品接受保留明确的人类验收。

## 原型与 HTML 方案说明

各领域采用同一说明结构：用户与问题、目标流程、角色与数据边界、页面/状态演示、设计决策、当前能力、目标缺口和验收方式。

两种成果分别标注：可演示原型展示交互，标明模拟数据和未连接能力；HTML 说明会解释方案与覆盖，不冒充可运行产品。HTML 从权威 Markdown/机器数据生成，保留源链接及生成检查，不手工修改 Event 生成页。其他领域先复用其处理方式，是否共享生成器由实现复杂度决定，不预先新增框架。

## 实施顺序与完成条件

1. 修正架构文档，建立总体入口、权威图与跨层原则；先解决已发现的路径和职责漂移。
2. 归整 UI/UX 与 QA 总体标准，确定 orientation 与需求追踪的统一格式。
3. 补齐页面制作/发布，制作首个非 Event 的说明 HTML 与交互原型，验证推广方法。
4. 补齐身份、三个 workspace、教会和小组管理；用权限及导航源码核实，不从角色名称推断授权。
5. 核对 Event 原始 YAML/EMBOK 来源及类型范围，补齐追踪；不另建已退役的通用 workflow 引擎。
6. 检查所有入口、链接、投影与需求覆盖，清楚保留未实现、未验证和待决策项目。

每个阶段交付可审查文档和证据后继续下一阶段。整体完成需四类功能规格、共同非功能标准、各域 AI orientation、状态追踪和两类原型/说明机制都有具体成果；仅有本计划不算补齐完成。文档补齐不意味着目标业务功能已实现。
