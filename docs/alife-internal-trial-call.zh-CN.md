# Alife 内部试用动员文案

## 致执事会与关心教会数位事工的同工

目前，Alife 已进入内部试用与稳定阶段。这代表它不再只是一个概念，也不只是开发中的技术项目，而是一个已经具备实际教会应用雏形、正在接受真实服事场景检验的平台。

现在正是一个很关键的时间点。

如果说前一阶段的重点是“把系统做出来”，那么现阶段的重点就是“让系统真正被教会使用、被同工检验、被事工场景打磨”，并且为正式进入实用阶段做好准备。

我们盼望执事会从教会整体治理与事工发展的角度，看见 Alife 的价值，也盼望有新的同工愿意加入试用，一起把这个平台从“可运行”推进到“可服事、可交托、可长期使用”。

## 一、为什么现在值得投入关注

教会的日常运作越来越需要稳定、清楚、可持续的线上工具。过去许多资讯和流程，往往分散在不同群组、个人对话、纸本记录、临时网页和口头传递之中，结果是：

- 会友不容易找到正确且最新的信息；
- 同工需要重复解释、重复整理、重复通知；
- 群组、活动、页面和讲道资料缺乏统一入口；
- 通知、报名和后续回复容易散落在不同聊天记录里；
- 网站维护常常依赖少数技术同工，难以长期交接。

Alife 的意义，不只是提供一个新 App，而是尝试为教会建立一个统一、清楚、可治理的数位事工基础。

它的方向很明确：

1. 让教会对外发布的信息更一致。
2. 让小组、事工和活动管理更有秩序。
3. 让会友在手机与网页上更容易找到需要的内容。
4. 让未来的维护与交接，不再完全依赖少数开发者。

## 二、Alife 已具备的功能特点

Alife 目前已经具备一套相当完整的教会平台骨架，重点包括以下几个方面。

### 1. 会员登录与身份识别

- 支持 LINE 登录流程。
- 系统会依据当前身份识别会员所属群组与可操作范围。
- 不同角色看到不同内容与入口，减少误操作与管理混乱。

这让平台更接近真实的教会成员关系，而不只是一个任何人都能随意进入的资讯页。

### 2. 群组与成员管理

- 支持教会主群组与下属群组结构。
- 支持成员申请加入、审批、拒绝、角色调整与移除。
- 支持群组页面浏览与群组管理分流。

这使系统很适合支撑小组牧养、课程班级、服事团队与阶段性活动编组。

### 3. 页面与内容发布能力

- 支持全站页面与群组页面。
- 页面支持中英双语标题与摘要。
- 页面支持区块式编写，方便分段整理信息。
- 页面具备 `Draft`、`Group`、`Public` 三种可见性，可分别对应草稿、内部成员阅读与公开发布。

这表示平台已经具备“教会官网 + 群组内容入口 + 内部资讯平台”的综合潜力。

### 4. 活动与报名流程

- 支持活动建立与活动资料呈现。
- 支持活动报名与后续回顾流程。
- 支持 AI 对话式辅助整理活动规划、报名和回顾草稿，但最终内容仍需要使用者确认后才保存。
- 适合未来扩展到课程、退修会、培训、探访行动或专题聚会。

### 5. 通知消息与回复

- 支持会员通知消息。
- 支持通知已读与回复流程。
- 有助于把部分审批、邀请、跟进和行政提醒从零散聊天中整理出来。

### 6. 讲道与信息汇整

- 支持讲道列表呈现。
- 支持讲道资料整理与同步机制。
- 有助于建立教会信息、装备材料与系列讲道的统一入口。

### 7. 手机友善、网页可访问

- 前端采用适合手机浏览的网页应用模式。
- 会友不需要学习复杂系统，也能直接从手机进入。
- 对教会日常发布消息、浏览页面、查看活动与参与报名非常实用。

## 三、值得向执事会说明的技术亮点

从事工角度看，技术不是目的；但从治理与长期维护角度看，技术路线会决定这个平台是否稳定、是否安全、是否值得继续投入。Alife 目前有几项值得注意的技术亮点。

### 1. 架构清楚，利于长期维护

后端采用分层架构，把核心规则、业务流程、资料存取与对外接口分开。这种做法的价值是：当教会以后要扩充功能、调整流程、换接外部服务时，系统比较不容易因为一次修改而牵动全局。

### 2. 登录与权限较安全

- 平台使用 HttpOnly Cookie 保存登录凭证。
- 权限不是写死在前端，而是按当前资料即时检查。
- 对成员、群组和管理权限的保护较完整。

这对于承载教会成员资料、群组资料和内部页面内容，是很重要的基础。

### 3. 支持手机端与现代网页应用体验

前端采用现代网页应用架构，兼顾桌面与手机浏览。这代表未来无论是会友查看聚会内容、同工整理页面，还是活动相关浏览，都可以在统一入口中完成。

### 4. 支持云端部署与持续演进

系统目前采用现代云端服务架构，前端、后端、资料库与边缘代理分工明确。这种做法的好处是：

- 日后部署更有弹性；
- 系统扩充与维护更有方向；
- 教会不需要一开始就背负沉重的自建基础设施压力。

### 5. 已经具备 AI 协助流程的延伸空间

在活动报名、回顾等流程中，系统已经预留并实现了 AI 辅助对话式流程的能力。对教会而言，这不是为了追逐流行，而是为了未来减少填写门槛、提升资料整理效率、帮助同工更快完成重复性流程。

换句话说，Alife 不是停留在传统网站层面，而是已经开始往“可持续演进的教会数位平台”迈进。

## 四、为什么现在需要新的同工加入试用

任何一个系统，若只经过开发者自己测试，通常只能证明“技术上可以运行”；但若要进入真正可使用的阶段，就必须让更多不同背景的同工来实际试用。

我们现在特别需要新的同工加入，原因很实际：

1. 新同工能更快发现哪些地方对第一次使用者还不够直观。
2. 非开发背景的同工能帮助判断页面是否容易浏览、活动信息是否容易理解、操作是否足够顺手。
3. 网站维护同工能帮助检验内容编排、双语页面、图片与区块结构是否适合日常服事。
4. 小组与行政同工能帮助判断成员管理、活动流程和页面更新是否符合真实服事需要。

系统要进入实用阶段，关键不是“功能已经很多”，而是“功能已经经得起真实同工使用”。

## 五、内部试用要怎么进行

建议本阶段的试用，不只是停留在看说明，而是要实际动手使用。试用可以从以下几类动作开始。

### 1. 构建系统，确认基本可运行性

建议参与试用的技术同工至少完成以下动作：

1. 后端构建：在仓库根目录执行 `dotnet build backend/Alife.sln -c Debug`。
2. 前端构建：进入前端目录后执行 `npm run build`。
3. 若需要本地完整浏览，可启动 API 与前端开发环境，分别访问本地服务页面。

这一步的目的，是确认系统在新的环境中仍然能被构建、被运行，而不是只在开发者自己的电脑上成立。

### 2. 浏览网页，检验信息组织是否清楚

建议试用同工实际浏览：

- 首页或主要入口页；
- 教会介绍类页面；
- 讲道入口页；
- 小组或事工页面；
- 页面中中英文标题、摘要与区块内容的呈现。

试用时重点观察：

- 第一次进入时是否容易理解；
- 重要信息是否容易找到；
- 手机浏览是否顺手；
- 页面内容是否有教会语境，是否容易维护；
- 公开页面与内部页面的边界是否清楚。

### 3. 浏览活动与相关流程，检验实际服事价值

建议实际体验：

- 进入活动页面；
- 查看活动资料是否完整；
- 尝试活动报名相关流程；
- 检查流程中的说明文字是否清楚；
- 判断整个活动体验是否真的能减少行政沟通成本。

如果活动页面能够被第一次使用者顺利理解并完成操作，就说明平台已经开始具备实用基础。

### 4. 站在服事现场来给反馈

我们需要的反馈，不只是“好不好看”，更包括：

- 会友是否知道下一步该做什么；
- 小组长是否能少花时间解释流程；
- 网站维护同工是否能容易更新内容；
- 执事会是否能放心把部分公开信息交给这套平台承载。

## 六、建议招募的试用同工类型

为让试用结果更接近真实使用，建议邀请以下类型的同工加入：

- 一位熟悉教会行政流程的同工；
- 一位负责网站或内容整理的同工；
- 一至两位小组或事工带领同工；
- 一些平常主要用手机浏览信息的会友；
- 一位能协助构建与基本排查的技术同工。

这样收集到的反馈会同时覆盖治理、内容、操作、视觉与技术稳定性几个层面。

## 七、对执事会的邀请与建议

现阶段最需要的，不是再等待所有功能“完全做满”，而是让教会在安全、可控的范围里开始真实试用。只有进入试用，才会知道哪些流程已经足够成熟，哪些地方还需要再打磨。

因此，建议执事会在这个阶段给予三方面支持：

1. 认可内部试用阶段的重要性，把它视为正式启用前必须经过的事工验证。
2. 鼓励新的同工参与，不只由开发者自己测试。
3. 允许平台在有限范围内承载真实内容、真实页面与真实活动流程，借此检验实用性。

这一步不是冒进，而是负责任地为正式使用做准备。

## 八、结语

Alife 已经不是一个停留在想法里的项目，也不是只属于技术团队的作品。它正在逐步成为教会可以共同拥有、共同检验、共同塑造的数位事工工具。

现在的内部试用与稳定阶段，非常关键。若有执事会的支持，有新的同工加入试用，并且愿意从构建、浏览网页、体验活动流程这些真实动作来检验系统，那么我们就有机会把它稳稳地推进到下一个阶段。

我们盼望的，不只是“上线一个 App”，而是预备一套真正能服务教会、减轻同工负担、提升信息整合能力，并为未来事工发展留下空间的平台。

现在，正是一起加入、一起试用、一起预备进入实用阶段的时候。
